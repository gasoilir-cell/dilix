# وصله‌های سرویسِ زنده‌ی `dilix-api`

اپِ موبایل و وب امروز به **`dilix-api`** روی پورت ۸۰۰۰ وصل می‌شوند
(`AppConfig.apiBaseUrl` → `http://185.55.226.250:8000`, مسیرها `/api/v1/...`)،
نه به سرویسِ `backend/services/core` این مخزن (پورت ۸۰۱۰، مسیرهای `/v1/...`).

سورسِ `dilix-api` فقط روی سرور است (`/var/www/dilix-api`) و **زیرِ کنترلِ نسخه
نیست**. تا وقتی مهاجرت به مونوریپو کامل نشده، هر تغییرِ آن سرویس اینجا به‌صورتِ
وصله‌ی قابلِ بازپخش نگه داشته می‌شود تا دستِ‌کم تاریخچه و امکانِ بازسازی داشته باشیم.

## محتوا

| فایل | نقش |
|---|---|
| `ratelimit.py` | ماژولِ سقفِ نرخ؛ مقصد: `/var/www/dilix-api/app/core/ratelimit.py` |
| `apply_ratelimit.py` | وصله‌زنِ idempotent روی `app/main.py` و `app/api/v1/auth/router.py` |

## اجرا

```bash
scp ratelimit.py apply_ratelimit.py root@185.55.226.250:/tmp/
ssh root@185.55.226.250 '
  cp /tmp/ratelimit.py /var/www/dilix-api/app/core/ratelimit.py &&
  python3 /tmp/apply_ratelimit.py &&
  systemctl restart dilix-api'
```

اسکریپت پیش از دست‌زدن به هر فایل نسخهٔ `.bak-<timestamp>` می‌سازد (قراردادِ خودِ
آن پروژه) و اگر وصله قبلاً خورده باشد کاری نمی‌کند.

## آنچه این وصله می‌بندد

- `POST /api/v1/auth/login` — پیش از این حدسِ نامحدودِ رمز. حالا ۱۰ در ۵ دقیقه.
- `POST /api/v1/auth/register` — ۵ در ساعت.
- `POST /api/v1/auth/otp/send` — ۵ در ۱۰ دقیقه برای هر IP، **و** ۳ در ۱۰ دقیقه
  برای هر شماره. cooldownِ ۳۰ ثانیه‌ایِ قبلی به‌تنهایی یعنی ۱۲۰ پیامک در ساعت
  روی شماره‌ی قربانی — با چرخاندنِ IP هم دور نمی‌خورد چون کلیدِ دوم خودِ شماره است.
- `POST /api/v1/auth/otp/verify` — ۱۰ در ۱۰ دقیقه. (`OTP_MAX_ATTEMPTS` فقط تلاش‌های
  *یک* کد را می‌شمرد و هر ارسالِ تازه صفرش می‌کرد.)
- `POST /api/v1/auth/oauth/{provider}` — ۲۰ در ۱۰ دقیقه.
- `POST /api/v1/auth/refresh` — ۶۰ در ۵ دقیقه.

متدهای `GET/HEAD/OPTIONS` شمرده نمی‌شوند تا `GET /me` که اپ مرتب صدا می‌زند به
سقف نخورد.

## نکته‌ی امنیتی: چرا `netutil.get_client_ip` اینجا استفاده نشد

آن تابع `X-Forwarded-For` را از هر فرستنده‌ای می‌پذیرد؛ برای لاگ و ژئو مشکلی
ندارد، ولی برای سقفِ نرخ فاجعه است: پورتِ ۸۰۰۰ مستقیم روی `0.0.0.0` باز است، پس
هر مهاجمی با یک سرآیندِ جعلی سقف را بی‌اثر می‌کرد. `rate_limit_ip` سرآیند را فقط
وقتی می‌پذیرد که خودِ اتصال از loopback یا شبکه‌ی خصوصی آمده باشد.
